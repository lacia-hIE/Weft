# 原生插件注册、配置与生命周期

Weft 的预置扩展通过同一插件目录注册。组合包继续使用原版 `package.json → dsh.bundle.patch`，目录中的 TypeScript 元数据只负责绑定可信模块、运行位置和配置 schema，不是新的安装协议。

## 注册来源

- `packages/native-composition/src/extensions.ts` 汇总随部署提供的组合包。
- 每个组合包声明原生 patch，以及条目的模块名、`host` / `client` 运行位置、原生 `Config`、启停字段和显示元数据。
- 服务端、浏览器分别维护预编译模块表。模块表是一份可信代码允许清单；用户配置不能注入模块代码。
- 目录验证重复 ID、模块名不一致、配置类型和启停字段。patch 中的配置作为原版设置命名空间的基础配置；已有配置命名空间和开关保留原来的持久化键。

同一个目录生成插件清单、组合包清单、配置命名空间和服务端加载计划。EnvironmentDO 处理通用注册项，不识别 JavaScript、文档转换或任务卡片等具体插件名称。

## 配置与管理

配置通过原版 `settings/describe`、`settings/update` 和配置 YAML 编辑，启停通过原版 `pluginManager` 接口处理。配置写入仍由原版适配层的 D1 队列串行化，不在插件管理层重复排队。

浏览器使用原版插件清单及设置接口取得启用状态和配置，监听原版变更事件与重连事件。任务管理插件只提供自身的 UI 和状态订阅，不负责加载其他插件，也不再请求专用的 `worker-plugins` 配置接口。

插件条目开关与组合包开关共同决定最终启用状态。必要的平台插件由注册声明保护。停用创建工具不会销毁它已经创建的后台任务；任务管理入口及沙箱权限联动继续运行。

## 生命周期

`packages/plugin-registry/src/lifecycle.ts` 提供前后端共用的协调器，串行处理配置更新、启停、移除和清理。失败的应用不会被记为成功，后续更新可重试；卸载和重复配置不会积累重复实例。

- 服务端驱动使用原版 Loader，配置更新使用原生 schema / volatile 行为，停用等待原生 Fiber 完成销毁。官方 profile 行的更新也复用同一 Loader 更新路径。服务端插件开关在下一轮开始前协调，保留正在运行的轮次。
- 浏览器驱动使用原生 `ctx.plugin`、Fiber 更新与销毁。变更事件触发通用协调器，不为单个功能编写启停分支。
- 沙箱、审批和具体工具的限制由对应插件负责。平台通过 `WorkspaceServices` 提供限定工作区的 RPC，插件不持有 Cloudflare binding；平台的租户鉴权与存储隔离继续在 DO 边界执行。

原版 Team 组合包的冻结会话语义、Agent 预设管理、第三方插件的审批与隔离 facet 仍保留各自的执行策略。这些安全和版本边界不因统一预置扩展的注册、配置和生命周期机制而改变。

## 新增普通扩展

新增可信工具或 UI 插件时，实现标准 Cordis 模块，声明原生 patch / Config，在部署目录及对应运行端的模块表登记。无需修改 EnvironmentDO 的管理分支、会话启动逻辑或前端入口。新增 Cloudflare binding 或平台权限时，需要另外实现并审核平台服务适配器。

CI 使用一个独立测试组合包验证新增条目能自动生成配置、清单和管理操作，并通过真实原版 Loader 完成加载、配置更新、停用、重新启用和移除。任务集成测试继续验证审批、刷新恢复和停用后取消任务。
